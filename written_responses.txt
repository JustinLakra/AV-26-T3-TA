### Part A - recover the data (CAN decode)

Comparing the CAN bus data in the video to step_test.log, I identified the following parts:
The first is the timestampEpoch, next is vcan0, which is probably the channel name, then the frame ID, and finally the data bytes.
Looking at the SteeringBench.dbc file, I am assuming that the data is split this way:
bits 0-16: MeasuredAngle,
bits 16-32: CmdAngularRate,
bits 32-48: SupplyMilliVolts,
bits 48-64: ActuatorTemp.

My assumption should be confirmed once I go over the explanation of a dbc file given in the resources. Not sure about the endianness, but I am assuming it is little-endian, since that is the most common.

Going through the dbc explanation resource, I found that the endianness is indeed little-endian because of the '@1' in the dbc file. The scale, offset and the min and max values are also given in the dbc file, so I can use those to find the physical values of the signals. I am assuming we have to clamp the values to the min and max values given in the dbc file, after calculating the physical values using the formula: physical_value = offset + scale * raw_value_decimal. The units are also given, making it easier to identify which values are to be decoded for part A.

Extracting the data and the IDs from the file was simple: I used the substring function to get them, then converted them to integers. For the data, I realized that i only had to read 32 bits, since the other 32 are not used for this part. I extracted the first 4 bytes, then applied a manual bitshift to switch the order to little-endian, then used that to calculate the physical values of the signals using the formula. Since the min/max values were given as [0,0], they were optional for the signals that I had to extract in this part. Also, the offset was also 0, so I only had to use the scale.

Frame ID kept: 0x200 or 512 in decimal.

Signal 1 (u_commanded):  byte position / endianness / signed? / scale / offset: 2-3 (bits: 16-31) (2 bytes or 16 bits) / little-endian / signed / 0.1 / 0
Signal 2 (y_measured):   byte position / endianness / signed? / scale / offset: 0-1 (bits: 0-15) (2 bytes or 16 bits) / little-endian / signed / 0.1 / 0

### Part B - identify system

Part B was to work out the actuator, and write the code down for it in plant.hpp. The Readme gave me the first few hints: first-order system with lag and one nonlinearity near the operating point.

So I searched up how to work out an actuator in a first-order system. I got the equation:
tau * dy(t)/dt + y(t) = K * u(t).
The constants were tau and K which were unknown, so to calculate them I did this (got the method through a google search):
We needed the slope of the graph in step_test, and then had to divide the slope by the step input, which was 15 deg/s. 
For change in y, I took the value to be 50 - 0, so the time had to be t50 - t0 (when the output started moving, not from when the command stepped). Calculating these, I got slope = 50 / 2.565, which was equal to approximately 19.493.
To calculate tau, I took the time at which the input stepped to 0, and the final value after settling. these values were 54.8 deg and 56.1 deg respectively.
Subtracting them, I got 1.3. Now this was the extra distance(angle) travelled by the system. So to find tau (time constant), I had to divide this by the speed at which the system was rising- which was the slope we calculated before.
Since time = distance / speed, dividing 1.3 by 19.493, gives us approximately 0.07 (something around 0.0699) for the time constant tau.

Now,
u(t) was u_cmd. and y(t) was the speed, but we needed the measured output angle in deg. 
Setting dy(t)/dt to be (y_n - y_o) / dt,
I rearranged the equation:
y_n = y_o + ((K * u(t) - y_o ) * dt ) / tau
Since dy(t)/dt meant a change in y with respect to time, I took y_n to be the new speed and y_o to be the previous speed which we store in the Struct Plant.
Now I calculated the angle, which was y_n * dt (distance = speed * time) and added it to the angle value in the Struct.
And then I just used the provided return statement. 

Next, I had to look at deadband_test near zero commanded rate, (which in this case was +/- 2) and figure out if the nonlinearity was a deadzone or a backlash.

Looking at the differences of both of those nonlinearities, a deadzone had no memory, and produced zero output with small inputs.
Meanwhile, a backlash had memory and lost motion when reversing direction. In the graph, u_commanded starts at +2, then after some time goes to -2. The y_measured graph rises linearly from 0 to somewhere around 2.5, and then flattens out and doesn't change afterwards.
This confirms that this is a backlash nonlinearity.

After running the previous code, I got 3 max err values- 2.5, 2.7 and 2.5
Searching up for figuring out backlash nonlinearity in an actuator, I got results saying that I have to calculate how much it deviates from the actual value, which I assumed the checks already do. 
Upon using the value 2.5 for the backlash, the checks told me that my values looked alright.

Proper justification for nonlinearity size (written as a comment as well in plant.hpp):
When I looked at the reversal_test without the backlash, the difference in y_predicted and y_measured was 2.5. Since backlash is when the motion is lost when reversing direction, the actual system is 2.5 deg behind the ideal angle. Also, one correction: since its idealAngle +/- 2.5, the size of the nonlinearity is 2 * 2.5 = 5.0 and not 2.5.

### Part C - control design choices

Used the formula kp * e(t) + ki * integral of e(t) + kd * derivative of e(t).
cmd reached values of around 3000 deg/s. The derivative was taken from the error, instead of the measured angle. 
This produced a false speed of the system- 3000 deg/s, and caused a command spike. When the target jumps, the error jumps as well, even though the system hasn't moved at all. Since we are dividing it by dt, it causes a massive spike in cmd.
So the fix was to work the speed out from the change in measured angles, which gives us the actual speed.

Next, There was too much noise, and after looking at this source: https://industrialmonitordirect.com/blogs/knowledgebase/pid-controller-tuning-kp-ki-kd-parameters-explained?srsltid=AU7gw4XcbiCxyKtGY6rQCluzT34LbmG6RzL3s0s8CXvy8WiGoFHme6cF I decided to use a low pass filter on the derivative.

Here's the source for the low pass filter I found on reddit: https://en.wikipedia.org/wiki/Low-pass_filter#Discrete-time_realization
I had to figure out RC, the time constant for the filter. The ticks in controller.csv are 0.005s apart, so the filter would go over just a single tick: this caused zero change in the graph.
For the filter to be meaningful, it had to go over more ticks. Assuming 10 ticks, per RC seconds, RC had to be greater than 0.02. 
We reach our target in around 1 second (based on the data), so an RC of 1.0 would be useless, since we would have already reached our target by then. Therefore, RC would have to be much less than 1.0, but also greater than 0.02.
I chose 0.05 for the RC value since it lies in between 0.1 (1 order of magnitude less than 1.0) and 0.02.

Now, for the values of kp, ki and kd, and tuning them. 
I went with the manual method of tuning these values, starting with kp = 2.0, and the rest all set to 0.0.
There was no overshoot, or err, but the time to settle was quite slow.
I tried increasing it further- 16.0 and there was overshoot, and the settling time had increased.
So I went back to 4.0- no overshoot and shorter time than 2.0.
Now, I tried increasing kd to 2.0- this significantly lowered the time, however there was still quite a lot of noise, even with the filter.
So after decreasing the value of kd, I finally found a value which worked quite well.
I went with kp and kd values of 3.4 and 0.110 respectively.

Now, increasing the ki even by 0.5 caused a massive increase in err, overshoot and time to settle.
Even with ki set to 0, there was no error or overshoot. Therefore, I decided to keep it at 0.0.

When changing the values of K, tau and backlash to 1.7, 0.1 and 3.0 respectively, I noticed that the on-centre trim improved, reversal improved in time but had err -0.10 and had overshot, and large move had err, overshot and was way slower.

No anti-windup since its a solution for the integral term accumulating and becoming too large and we have ki set to 0.0, so it isn't required.
